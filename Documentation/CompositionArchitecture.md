# SharpEngine 组合式开发架构

本页记录已确认的开发基线，适用于引擎功能和项目侧引擎扩展的新增与修改。现有功能需要逐项核查；本页不代表已经实现通用组合框架、任意嵌套资产格式或全仓架构迁移。

## 1. 组合式金字塔

功能按能力与依赖形成无环的单向层级。基础功能可以被多个上层引用，若干子功能可以封装成完整组合，组合后的能力又可以被其他功能继续引用。层级由依赖关系决定，不要求固定层数，也不要求一个功能对应一个程序集。

- 组合功能依赖子功能的公共契约；子功能不依赖具体组合功能、调用者或最终应用。
- 需要回调时，由下层声明所需接口、事件或输出契约，上层提供实现。调用时的回调方向不等于反向的代码依赖。
- 拒绝直接或间接依赖环。共享基础能力应下沉到其合适的所属层，不通过服务定位器或全局单例隐藏循环依赖。
- 功能可以复用同一套下层定义；具有可变状态的使用实例应明确自己的数据、生命周期和所有者。

金字塔描述能力的逐层组合；代码依赖可以复用下层节点，形成有向无环图，不要求每个下层功能只有一个使用方。

## 2. 类型决定组合边界

每个领域通过自己的能力契约声明组合插槽的输入类型，例如播放组合接收 `IPlayable`，移动修饰器组合接收 `ICharacterMovementModifier`。未实现对应契约的类型不能进入该插槽，尽量在编译期表达这个限制。

接口声明该领域实际需要的操作和数据语义。不要引入一个能装入所有功能、再通过字符串、类型判断或强制转换决定行为的万能 `IComposable` 容器。序列化后的类型选择仍须注册和校验，不能把编译期类型约束当作资产安全校验。

“顶层”是某个组合关系中的类型边界。没有暴露对应可组合契约的最终功能不能被塞入该领域的组合。不要用目录位置、类名、功能大小或一张人工维护的顶层名单代替类型约束。一个功能可以向另一个领域暴露完整契约，从而作为另一个组合的子功能。

## 3. 组合体封装细节

调用方只依赖组合体公开的完整能力，不需要知道内部有几个子功能、使用哪种播放方式或怎样安排内部步骤。子功能通过自己的公共入口仍可独立复用；复用子功能不要求先创建一个无关的上层组合。

组合体可以定义自己的对外接口。只有存在同一使用位置上的替换需求时，基础单元与组合体才实现相同接口；不强制所有组合体继承基础单元的接口。不要为了访问子功能而公开内部对象图或要求调用方逐层穿透组合体。

组合点的契约明确所需输入、输出、状态写入权和适用阶段。按实际需要提供可替换的子功能插槽，不把每个私有方法都变成扩展点，也不要求所有方法可继承或可重写。需要增加能力时，先检查既有子功能能否组合，再判断是否需要新增领域契约。

## 4. 功能定义、模板与实例数据

大部分功能的逻辑和定义是模板化、可复用的，使用时的数据是实例化的。这里的模板化不预设使用 C# 泛型、某一种资产文件或某一个基类。

| 层面 | 内容与归属 |
| --- | --- |
| 功能定义 | 算法、领域契约和组合结构的定义，可被不同功能引用 |
| 模板配置 | 本次使用所依据的参数、资产及子功能选择；按所属格式保存与校验 |
| 使用实例 | 当前调用/运行所需的进度、暂停、取消、结果、缓存和资源；归属于具体使用方 |

两个组合可以引用同一功能定义和只读资产，但不应因此共享播放进度或其他可变执行数据。同一个定义被多次使用时，实例身份不能只靠定义/资产 ID 区分。采用该领域现有的实例身份和所有者作用域；不要为纯计算值或无状态小对象强加全局注册身份。

如果算法对象本身持有游标、进度或缓存，它已承担实例职责，不能只因名字是 Template 就无条件共享。显式共享服务必须说明状态归属、使用范围和并发/销毁约束。不要把实例数据放进静态字段或共享模板，导致两个使用方互相改变行为。

可序列化配置、运行实例和原生资源分别遵守既有组件/资产契约：Authoring 修改走事务，Runtime 普通字段允许业务代码写入，运行状态不自动回写模板或源资产。

## 5. 嵌套执行与生命周期

组合实例负责驱动其拥有的内部子实例。内部实例不因嵌套而再次自动加入全局 Tick，不得同时由父组合和全局调度重复推进。具体功能可以有显式的子步、求值或多次采样，但必须区分采样与推进自身时间/状态。

引擎继续掌握 World 组件生命周期及固定阶段。组合体在所属阶段内执行领域逻辑，不创建第二套可配置的组件生命周期排序。已经由 World 管理的组件只是被引用，不由组合体再次初始化、Tick 或销毁。

明确拥有与借用：拥有者负责其子实例的创建、停止、取消和释放；借用者不能擅自释放共享服务、外部组件或资产。失败清理和失效行为遵守具体领域契约，不承诺任意外部副作用都可回滚。

嵌套组合必须保留所属阶段和最终状态写入边界。移动模式、修饰器等可以组合计算意图或增量，但目标 Transform 仍由明确的移动权威在规定边界提交。组合不能隐含增加第二个写入者。

## 6. Module、Plugin 与组件的职责

功能组合、构建依赖、分发启用和 World 生命周期是不同的边界：

- 普通函数或对象可以承载功能逻辑，不强制每个子功能继承 `SharpComponent`。
- `SharpComponent` 承载需要 World 身份、配置、生命周期及观察能力的功能接入。
- Module 是构建/程序集和模块注册边界；同一 Module 内可以有多个可复用功能。
- Plugin 是 Module 与内容的分发、发现和项目启用容器，不引入第二套功能生命周期。
- Runtime 功能不依赖 Editor。Editor UI 是领域能力的使用方，不是底层功能必须依赖的宿主。

Module/Plugin 的当前规则以 [ProjectOrganization](ProjectOrganization.md) 为准。不要为了每个组合节点创建 Module、Plugin、MCP 入口或一套额外 manifest。

基础设施、内容适配和具体预览的分层示例见 [基础设施与组合层](EngineArchitecture.md)。本页维护通用的组合、类型和实例契约，该专题维护视口等基础设施的具体接入与隔离要求。

## 7. 序列化、观察与当前实现边界

嵌套不等于允许序列化任意 CLR 对象图。组件配置继续使用生成描述符、受支持字段和稳定引用。当前组件格式不支持任意接口/多态字段或循环托管对象图；新增可保存的组合结构必须单独设计其版本、类型注册、引用和依赖发现，不能绕过已有校验。

需要 AI/Inspector 观察的语义状态在所属实例的完整提交边界可读。组合体公开自己的配置、状态和诊断，并按实际需要提供可发现的子实例路径。封装不要求公开全部内部对象，也不允许隐藏影响行为的实例状态。新增观察契约仍须定义身份、版本和 revision。

当前可参考的实现包括 `TimelinePlayable` 的组合求值和 CharacterMovement 的模式/修饰器组合，但必须继续检查其实际状态所有权和调度路径。参考例子不表示整个领域已通过本架构的所有检查。

## 8. 开发审查与验收

设计与审查一个可复用功能时，明确以下内容：

1. 功能对外契约、适用的类型化组合插槽，以及所依赖的下层能力。
2. 功能定义/模板配置与每次使用实例数据的分界。
3. 子功能能否通过自己的公共入口独立复用，组合体是否封装内部步骤。
4. 子实例的拥有者、借用关系、执行阶段和唯一状态写入者。
5. 适用的序列化、资产依赖、诊断、观察和版本规则。

按变更验证有意义的行为：同一功能定义的两个使用实例互不污染；组合嵌套后仍满足其对外能力；拥有者停止/释放不会影响其他实例；没有重复调度或反向依赖。测试当前实际支持的组合，不以文档声明替代实现验证。

开发及交付流程由仓库 `sharpengine-development` skill 约束；使用方式和公开 API 的变更同步更新当前版本引擎手册。
